# Case study: ReachGuard

## The problem

Cold-outreach automation tends to fail in three ways: it emails people it should never have emailed (role accounts, dead domains, people who opted out), it lets a language model write claims nobody checked, and it can send the same message twice when two workers race. ReachGuard is built around making each of those failures hard to commit.

## The approach

- A Postgres state machine decides what each lead can do next, so a workflow bug cannot move a lead somewhere illegal.
- Stages pull work with leases, so concurrent workers cannot take the same lead and crashed workers do not lose leads.
- Models propose; deterministic code decides. Claims must quote a snippet found on the page, copy passes code checks before and after a separate judge, and unsubscribe handling runs a keyword rule before any model.

## What the evaluation measured

All numbers below come from `docs/EVAL_REPORT.md`, generated by `scripts/eval-local.sh` on a throwaway Postgres with the rg-tools service. They are sandbox measurements on synthetic data that I wrote, not production results.

| Check | Result |
|---|---|
| Planted bad leads caught by the hygiene rules with the right reason | 23 of 23 |
| Clean leads blocked by those rules | 0 of 31 |
| Planted bad drafts that the deterministic precheck can detect, caught | 12 of 12 |
| Clean drafts failed by the precheck | 0 of 6 |
| Labeled replies with unsubscribe intent hit by the keyword rule | 5 of 5 |
| Replies without unsubscribe intent wrongly hit | 0 of 35 |
| Concurrent duplicate scenarios absorbed (same lead x20, same email under different keys x20, event replay x20, send scheduling x20) | 4 of 4 |
| Claim, lease and release scenarios (no overlap across workers, lease expiry, dead letter at cap) | 3 of 3 |

The concurrency check found a real defect before it was fixed: twenty simultaneous inserts of the same email under different idempotency keys raised unique-violation errors in nine of them (one row was still stored). The insert now absorbs any unique conflict.

## What was not measured

The model-dependent parts did not run in the committed report because no model key was available: judge catch rate on the 30 planted drafts, prompt-injection resistance, reply classification accuracy, LLM cost per lead and stage latency. The 60-lead end-to-end run and the stack-level fault tests (provider outage, worker crash, Redis restart) also need the running n8n stack and were not run. No live vendor, mailbox or real n8n import has been exercised by the committed tests.

## Stack

n8n in queue mode, PostgreSQL 16, Redis, Fastify and TypeScript service (Zod, Ajv, Vitest), Mailpit, Metabase, Telegram, Docker Compose, GitHub Actions.
